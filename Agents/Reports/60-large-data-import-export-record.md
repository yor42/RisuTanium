## 2. The `.bin` speed batch (`b6d8e963`)

**Why.** The maintainer asked on 2026-10-05, while 1c was being planned, whether the `.bin` import and export could be sped up now that account sync and Drive were gone (`MC-197` 1).

**Investigation (row 1182, `investigator`).** The slow paths were not behind `isAccount`, so removing account sync bought no speed (refuted). MEASURED on synthetic data, an i9-class desktop, Node: the restore's `remainingBuffer` concatenation was quadratic (a 155 MB entry took 29.1 s at 64 KB chunks and 1.9 s at 1 MB chunks); the fixed `sleep(10)` per restored entry (`backuplocal.ts:613`, before `b6d8e963`) cost about ten times the disk work; on Tauri, four appends per entry took 22.65 s against 0.28 s coalesced, per 20,000 x 32 KiB. The packet ranked R1 to R10 and proposed no container change. A second investigation (row 1183) TRACED that the web, Node and PWA exports all went through `LocalWriter.init` to `streamSaver.createWriteStream` with the default helper page on `jimmywarting.github.io`, with no timeout or fallback; the offline hang was INFERRED (not run).

**Plan and Gate 1 (rows 1185 to 1187).** Revision 1 had items B1 to B6 (B6 was found while planning: the `sleep(10)` kept a Node restore under `storageRouteLimiter`'s 20,000 requests a minute, and `nodeHttpStore` had no 429 handling). Round 1 `[REJECT]` (M1 to M5, m1 to m12); the maintainer chose, for a plain-HTTP export, "Outside popup, else memory (Recommended)", and for Node restore assets over the body limit, "Warn first, then skip (Recommended)" (`MC-197` 4). Round 2 `[REJECT]` (N1: the probe resolved on stream handover; N2: cold units sized uncompressed); at the second rejection the Orchestrator replaced the mechanism with a vendored, patched streamsaver and a worker `{download}` handshake and dropped the dependency. Round 3 `[EDITORIAL]` (E1 to E5; a `vi.mock('streamsaver')` count of 35).

**Implementation (rows 1188, 1189).** Two parallel `sonnet-coder` runs in `C:\Projects\RisuAI-bin` under file ownership: the restore side (262,689 tokens) and the export side (231,537 tokens). The export coder put the writers in a new `src/ts/exportWriters.ts` (a test seam) and `pnpm install --lockfile-only --offline` updated the lockfile.

**What the commit message states.** Restore: the encryption-marker walk records each entry's offset and length and each entry is read once with `slice()` (the container is unchanged); the 10 ms sleep is replaced by a yield about every 50 ms; on the Node server, assets over the body limit are listed and the user confirms skipping them before anything is written; the Node byte store retries a 429 on every request (at most 5 tries and 90 s per call). ## 5. Batched Rust asset I/O for desktop restore and export (`b5a41e3d`)

**Plan and Gate 1 (rows 1256 and 1257).** An `investigator` groundwork run (row 1249) found that the prototype source was lost, that the Android branch already used `write_chunk` and `read_range` (2 calls per asset), that a raw body is unreadable on Android, that assets were not fsynced at that time, and that the export output appends are a second cost. The plan `[REJECT]`ed in round 1 (R-1 an oversize entry is unfsynced; R-2 byte budget; R-3 export read rules; R-4 a single drain point; R-5 Tauri-mode guards on both paths; R-6 a new-directory parent flush; O-1 to O-8; the Orchestrator verified R-3 and R-6 in source) and was `[EDITORIAL]` in round 2 (E-1 a duplicate-key hold-back could wait on the unsent batch; E-2 the JSON-array fallback contradicts I8, so "not raw" means batching is unavailable for the page; E-3 no read or send after an observed error). The reviewer's Windows path-normalisation traversal experiment was negative. Revision 3 was accepted.

**What the commit message states.** Four Rust commands in `src-tauri/src/asset_batch.rs`: `put_assets_batch` (a raw body of length-prefixed frames, parsed whole before any write, up to 4 worker threads, keys equal after case folding routed to one worker in order), `put_asset_single`, `get_assets_batch` and `list_assets_sized`. No command takes a filesystem path; writes need the `assets/` prefix and the key rules. Each file is written to a temp file in its target's directory, flushed with `sync_all` and renamed over the target; the directories that received a rename, and the parents of directories the call created, are flushed best effort. The per-file fsync of restored assets is the maintainer's decision (`MC-197` 9). The JS pipeline (`assetBatchPipeline.ts`) sends batches of about 4 MiB (at most 256 entries), at most 4 calls in flight and at most 16 MiB in flight; an entry over the budget goes through `put_asset_single` alone; availability is fail-closed to Tauri on Windows, Linux and macOS.

**Implementation and Gate 2 (rows 1258 to 1262).** Two parallel `sonnet-coder` runs (Rust and JS) under a shared contract; the JS coder mutated `backuplocal.ts` in place once and reverted it (a process breach noted for the reviewer; the reviewer found the drain line intact). Orchestrator pre-gate: full suite 498 files, 9883 passed, 6 skipped; `pnpm check` 0/0; build OK; `cargo test` 71 passed. Round 1 `[REJECT]` on tests only, with no production data-safety defect: F1 (the export drain unpinned; the `exportNoClose` mutant survives), F2 (no entry read after a failure unpinned; `loopIgnoresFailure` survives), F3 (a test header overclaimed), F4 (a fold comment overclaimed: NTFS and APFS treat long s, final sigma and micro as one name), F5 (the batch-path run titled "reproducer"). *Reviewer-run:* 15 of 19 JS and 10 of 11 Rust mutants killed. Orchestrator-run after remediation: full suite 9886 passed, 6 skipped; `pnpm check` 0/0; build OK; `cargo test` 74.

**Live check A11 (row 1263, MEASURED, Windows desktop, i9).** The 31,069-asset slice: restore 66 s (461 s before), export 55 to 57 s (184 s before); every asset SHA-256 equal; the export's database decodes equal to the old build's; a restore of the new export boots. ## 7. Bounded IPC for large entries and user files (`bc631526`)

**Cause (row 1266, `perf-analyzer`, MEASURED, n=1 to 3).** WebView2 allocates one contiguous buffer per IPC call, 4 times the request body (plus about 2 KB of headers) and 2 times the response body, and refuses one above `0x7FE00000`. A request is therefore limited to about 511.5 MiB (536,342,528 bytes passed, 536,346,624 crashed) and a response to about 1,023 MiB; the page cannot hold one buffer above 2,046 MiB. This corrects the first live check: the crash is in the browser process, and Rust's true peaks at 256 MiB were 2.57 against 2.45 GB (the `to_vec` copy is about 5%); the 1.55 and 1.29 GB figures in the `b5a41e3d` commit message were sampler undercounts (the message says "up to", sampled every 2 s). Throughput is flat from 4 MiB per call upward.

**Plan and Gate 1 (rows 1268 and 1269).** Round 1 `[REJECT]` (F1 to F9), round 2 `[EDITORIAL]` (R1 to R5); revision 3 accepted. The default chosen, and told to the maintainer: an incomplete export file is deleted. The maintainer accepted that an export stops with an error when an asset changes during it (`MC-197` 12).

**Implementation and Gate 2.** A Rust coder, a JS part-1 coder, a move onto `30d3e594` in `RisuAI-bigentry2` and a JS part-2 coder (rows 1272 to 1275). In the move the coder used `git restore --staged -- .` in its own worktree instead of explicit paths (harmless; a note for briefs). Gate 2 round 1 (row 1276, about 331k tokens) `[REJECT]`: two untested data guards (the u32 header check; the `touchedFile` no-delete), mutants survive; the behaviour otherwise sound. Remediation added both tests (mutants m1 to m4 killed). Round 2 `[EDITORIAL]` (the `headerReadLength` comment, the "about 4.29 GB" wording, the `runExport` doc), fixed and verified. Four new strings in six locales (row 1280).

**What the commit message states.** Every desktop IPC call that moves file payload stays at or below 4 MiB (`CHUNK_MAX`). Restore streams an asset above 4 MiB to disk in 4 MiB pieces through a new raw `write_chunk_raw`; `put_asset_single` is removed. `get_assets_batch` enforces a 4 MiB response limit in Rust (new statuses 4, large, and 5, deferred). Export streams every asset the batch read cannot deliver within 4 MiB, writes the entry header from the total in the first `read_range` trailer, and stops when an asset changes, vanishes or cannot be read. Opening or importing a large user file from outside the app folder reads it in 4 MiB calls and a download is written in 4 MiB appends. Boot sweeps every nested temp location (`sweepAllWriteTemps()`). `capabilities/migrated.json` adds `fs:allow-open` and `fs:allow-read` (`fs:allow-open` can also open for write, so it is not a read-only grant; net reach is unchanged only because `fs:allow-write-file` is already granted). Behaviour changes: an export that fails now ends with a message instead of the global alert and never reports "Backup Successful"; a TauriWriter export that made a write call and then failed deletes the incomplete file (or says it could not); an asset of 4 GiB or more fails the export with `backupFailedAssetTooLarge` (the old build crashed here); it is not skipped, so the export cannot succeed until the asset is removed or made smaller. CHORE-129 replaces that failure with the warn-and-leave-out check of `MC-223`.

**Live acceptance (row 1281; commit message figures; MEASURED, n=1, Windows; Defender real-time scanning was on for S10).**
- S1: a 5.1 GB `.bin` with assets of 600 MiB, 1.5 GiB, 2.5 GiB and 0 bytes plus 296 small ones restored in 69 s, all 300 asset hashes equal, no IPC call above 4 MiB (`write_chunk_raw` n=1,189); the old build `b5a41e3d` died at 5 s. The asset phase is flat at about +110 MiB; the whole restore peaks +1,211 MiB, in the tail that decodes the 159 MB legacy database (a control with 300 small entries peaks +1,131 MiB). ## 8. The streaming importer (`64436cbd`)

**Scope** (the maintainer's four answers, `MC-225` 2): `.risum`, desktop open-with and PNG card assets; 200 MB per asset (like `.charx`, `MC-187`), any size for the file as a whole; on Node a pre-check and message for an asset over 100 MB with no server change; the whole file's structure is validated before any asset is saved. `.json` and `.risup` are unchanged.

**Plan and Gate 1 (rows 1283 to 1285).** An investigation (about 217k tokens) fed the plan. Round 1 `[REJECT]`: B1 (concurrent handle reads), B2 (new 50 MiB limits would refuse legacy inline-asset cards from `5f2275eb~1`), B3 (the Tavern refusal), B4 (seek and fstat permissions and the source's lifetime), B5 (non-failing reproducers). Round 2 `[EDITORIAL]` (E1 to E5: the 32-bit V8 ceiling, PNG pass-2 checks, exact reference rules, a single low-level-access prompt, wording); plan revision 3.

**Implementation and Gate 2 (rows 1286 to 1291).** Stage A (`.risum`, about 361k tokens) and stage B (PNG, about 250k tokens) by `sonnet-coder`; five new strings translated; Gate 2 round 1 `[EDITORIAL]` (E-1 to E-3 and optional items 1 to 3 folded in by `test-warrior`), round 2 `[EDITORIAL]` (the commit message's "several times" became "at least twice"). Checks: full vitest 513 files, 10423 passed, 6 skipped; `pnpm check` 0/0.

**What the commit message states.** Both formats are imported in two passes: pass 1 walks the file by offset and checks it without saving anything; pass 2 reads one asset at a time and saves it. Refusals happen before any save (bad magic, version or type, a cut file, a record count that does not match the module's asset list, an asset over the limit, a missing or non-JSON card chunk, a missing `__asset:` or `embeded://` reference, a declined or wrong rcc password); the low-level-access prompt for PNG cards is asked once. The per-asset limit is 200 MiB, or 100 MiB on Node. A change in the file's size, modified time or a record's mark or length between the passes stops the import with a "file changed or could not be read" message, outside the save-retry loop. Desktop open-with reads through plugin-fs handles (`open`, `seek`, `fstat`, `read`), at most 4 MiB per call; `fs:allow-seek` and `fs:allow-fstat` are added (handle-only). Deliberate behaviour changes: a module whose record count differs from its asset list is refused; an old Tavern PNG (no v2 or v3 spec) no longer saves its asset chunks (nothing references them); a PNG asset of exactly 200 MiB is refused (pass 1 estimates the size from the base64 length) while `.charx` accepts it; 1 to 7 trailing bytes after the last full PNG chunk are not kept. Accepted deviation: an append after the module's terminator during desktop pass 2 is undetected (the imported data is correct). Not covered: assets saved in pass 2 before a save failure or a file change stay behind (CHORE-101).

**Live acceptance (row 1292, MEASURED, n=1; memory is process-tree private MiB above baseline).** Desktop, a 2.32 GiB `.risum` (3,010 records including 10 x 180 MiB): imports through Settings > Modules, drop and open-with, all asset SHA-256 equal, +571 to +661 MiB, open-with reads at most 4 MiB per call and closes the handle once; the build before fails every route (open-with: "Array buffer allocation failed" at +2,401). A 10,000-record module: pass 2 about 106 to 116 s. A 2.9 GB PNG card with 11 x 190 MiB assets: imports, hashes equal, +1,354 (before: +3,258); a card with a 210 MiB asset is refused in about 1 s naming the asset. Chrome web build: the 2.32 GiB `.risum` imports (+728). Node-hosted: a module with a 120 MiB asset is refused with the 100 MB message and nothing is written. Android (Note 9, debug build): a 626 MB `.risum` imports, large hashes equal, renderer up to about 1.2 GiB, no crash. A file changed during import stops with the "changed" message.

## 9. Piece-by-piece hashing and saving (`1e71c45c`) and the Note 9 incidents

**Why.** After section 8 a PNG card import with 190 MiB assets still peaked at +1,354 MiB (several whole copies: the base64 text, the decoded bytes, Web Crypto's copy inferred, and a write copy on web and Node).

**Plan and Gate 1 (rows 1299 to 1302).** An investigation (about 114k tokens) found that hashing alone removes one copy and that the save must also go in pieces; `@aws-crypto/sha256-js` was already a dependency (173 MiB/s MEASURED on the i9); `saveAsset` falls back to `uuidv4()` without `crypto.subtle`; the Node cap is 100 MiB. The maintainer answered (`MC-225` 5): desktop and Android first, web next; plain HTTP to content-hash keys; Node at 100 MiB. A Note 9 measurement (about 46k tokens): the owned JS SHA-256 ran 78 to 88 MiB/s in the foreground and about 7 MiB/s with the screen off, while `crypto.subtle` ran 615 to 760 MiB/s (hashing stays in JS). Gate 1 round 1 `[REJECT]` (about 197k tokens): `@aws-crypto/sha256-js` 5.2.0 gives the wrong SHA-256 at 512 MiB and above (the high length word is written little-endian; executed); an in-place `rpack` decode corrupts a retry; a writer's pending view against a reused buffer; a read-2 mismatch was not mapped to file-changed. Revision 2: one read and a Rust final key on the last chunk (exists means discard). Round 2 `[EDITORIAL]` (T9 and I9 overclaim, T7 and T8 labels, a stale header); revision 3. `blockKeys.ts` keeps `@aws-crypto` (short names only; upstream-relevant).

**What the commit message states.** On the Tauri desktop and Android app an asset of 16 MiB or more is read from the file at most 4 MiB at a time, and each piece is hashed and written once, so the asset is never held whole; smaller assets are saved as before. `src/ts/assetHash.ts` holds an incremental SHA-256 core of our own, because the library gives the wrong digest at 512 MiB and above; `sha256Hex` uses `crypto.subtle` when present. The Rust chunked write's last chunk may carry a final key: the temp file is renamed to it or discarded if the key already exists; no partial file appears under an asset key. Plain-HTTP hosts now save assets under the content-hash key (`assets/<sha256 hex>.<ext>`) instead of a random UUID key; keys are otherwise identical, so exported files and upstream imports are unaffected. A read error, short read, header mismatch or size or modified-time change ends the import with the existing file-changed message and leaves no file under the key in progress; assets saved earlier in the same import stay. Web and Node otherwise behave as before (Node keeps 100 MiB; there is no chunk endpoint).

**Gate 2 and checks (rows 1303 to 1308).** Stage A (about 243k tokens) and stage B (about 205k); Gate 2 (about 216k) accepted; a commit-message fact-check (about 21k), an editorial pass (about 48k) and a `doc-writer` commit-message draft (about 49k). `cargo test --lib` 133 passed; full vitest 517 files, 10533 passed, 6 skipped; `pnpm check` 0/0; build OK. Red evidence is against `64436cbd`.

**Live acceptance (row 1309, `perf-analyzer`, about 236k tokens, 154 tool uses, about 85 min; H1 to H6 all PASS; MEASURED, single foreground runs, release builds on the i9, debug builds on the Note 9).**
