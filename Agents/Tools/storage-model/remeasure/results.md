## Task 1: S0-8 root-write series (P5, A2)

### Method
New harness, not the author's code. World: the full T4 store (1000 characters, 2055 chats, core units at real sizes, every chat's chunk keys, the 50 000-message T5 chat on character 0 as 232 (128 KiB cap) or 155 (192 KiB cap) real chunk bodies, 7 fixed blocks at real sizes incl. 7.8 MB modules, 16 shards, manifest, commit key; messages 200-899 B of ASCII prose, 15 % of odd messages with generationInfo). Store model = the planned IndexedDB shape: one object store, plain `Uint8Array` values, no per-key version wrapper. Commit arms:
- `tx1-strict` = the plan's design: ONE readwrite transaction with `durability: 'strict'`: get commit key, compare bytes, put tail + shard + manifest (+ root unit) + commit key.
- `tx1-default` = same, default durability.
- `ntx-default` = the author's shape for comparison: one transaction per unit, then a CAS transaction.
Variants: `base` (tail, shard, manifest, commit = 4 keys); `root18` / `root59` (per-send fields stay in the root: a new root unit is written on every append, 18 470 B = T4 root, 59 000 B = S0-12 root; 5 keys); `ctail` (the per-send fields, 2 KiB: messages counter, 8 reloadKeys, lastMemory 2 KiB, isStreaming, chatId stamp, live inside the tail chunk; 4 keys); `cshard` (the same fields in the chat's index-entry inside the shard; 4 keys). Time covers tail stringify/encode, shard stringify (shard 41.5 KiB), manifest and commit serialisation, and the store round trip, to `oncomplete`. Bytes = sum of value bytes of every put (key bytes are about 0.2 KiB more). Every cell is measured at five fill points (empty tail, 25, 50, 75 %, and "max" = the largest tail that still accepts one more message) x R=40, interleaved in a seeded shuffled order: n=200 per cell pooled, n=40 at the maximal tail ("full-tail"). Untimed steady-state GC stand-in: the keys written three commits earlier are deleted after each commit (the author left garbage in place and cleaned up per run).

## Task 2: S0-5b 16-shard mark (P6)

### Method
Same full T4 world as Task 1, built with the full key list: 1000 core units, EVERY chat's chunk keys (2 593 chunk keys for the 2 055 T4 chats at the 128 KiB cap, 16-byte placeholder bodies, the mark never reads bodies; plus 232 real T5 chunk keys, 7 fixed blocks), shards, manifests, then 100 garbage appends (1 tx each). `realistic` = current + 20 retained manifests after those appends (36 distinct shards at 16 shards, 84 at 64; 241 garbage keys listed); `worst` = 20 further all-shard commits so all 21 manifests name distinct complete 1000-character indexes (336 shards at 16, 1 344 at 64; 301 garbage keys). Mark = plan A1.2: five prefix-range `getAllKeys` (u/, m/, s/, ch/, f/), read the commit key, read 21 manifests, read and parse every distinct shard, build the marked set, count candidates. No body reads (counter recorded, zero in every run, by construction). Three read modes per iteration, interleaved with rotating order: `seq` (everything sequential), `par8` (8 reads at a time, manifests and shards), `tx1` (one readonly transaction with all gets issued at once). n=20 iterations per cell on the Note 9. List time is reported separately; parsing happens after the reads of each phase (CPU part reported). Chunking: bytes-128KiB (primary) and count-200 (the author's), shard counts 16 and 64.

## Task 3: P10 two-tab plain-HTTP probe

### Method
Two tabs of the same origin, one database (`p10-probe`), one object store, a `cas` key plus a `witness` key and two 1 KiB pads. Each probe is ONE readwrite transaction built only from request callbacks (no awaits), in the order: put `witness` = own token; get `cas` (c1); get pad1; get pad2; put a 64 KiB unit; get `cas` again (c2); get `witness`; decide. Modes: `cas` = stale-base compare-and-swap like the planned commit (the tab reads the rev in a separate transaction, then in the probe writes `cas = base+1` only if `c1.rev === base`); `rmw` = blind read-modify-write (`cas = c1.rev + 1`); `split` = positive control, a deliberately non-atomic read-modify-write (read in one transaction, write in another). Interleaving checks per transaction: `c2.rev !== c1.rev` (another transaction committed a cas write while mine was open), `witness !== own token`; per phase: lost updates (`won - (rev1 - rev0)`), duplicate winning bases (two tabs both succeeded from the same base), gaps, and wall-clock overlap of the two tabs' executing windows (first-request callback to last-request callback; in the serialised world these windows cannot overlap). Phases: `cas` and `rmw` with `strict` and with default durability, then the control. Desktop: 30 s per phase, one round. Note 9: 40 s per phase, three rounds (tabs re-foregrounded in turn before each phase, see below). Origin, context: see Environment; both tabs report `isSecureContext` false, `navigator.locks` undefined, `crypto.subtle` undefined. Data: `out/p10-desktop.json`, `out/p10-n9.json`.

Observation that must travel with it (UNEXPLAINED, not root-caused): on the Note 9 a tab that has been hidden (the earlier tab when a second tab is opened over adb) stopped completing its IndexedDB callbacks after about a minute hidden (watchdog `out/p10-diag-n9-poll10s.json`: tab A's last completion at 57 s, 1 045 iterations, then no progress until it was foregrounded; `evaluate("1+1")` in it still answered, a new IndexedDB read in it hung). A GC or commit in a hidden tab may take unbounded time to finish.

## Deviations from the author's method and limits
1. New harness, own code, not the S0-8 `alite.mjs`: plain `Uint8Array` values (no `{bytes, version}` wrapper), planned single-transaction commit as the primary arm (the author used one transaction per call), strict durability arm added (the author used default durability only), index entries and chunk plans own implementation from `t4-stats.json`, T5 messages own generator with the same size law.
2. Root series n: 200 per cell (5 fill points x 40) instead of 50, and p95 by nearest rank (the author's `floor(n*0.95)` index is the maximum for n<=19, the second highest at n=20-39). Maximum fill point is "largest tail that still takes one more message" instead of "99 % of count".
3. Untimed GC stand-in deleted garbage every append (author: none, DB cleaned per run); this keeps the database near its starting size and so includes the cost of background deletion noise, not the growth of an ever-larger database.
4. i9 figures for Tasks 1 and 2 are desktop Chrome 155 IndexedDB, not Node HTTP/mem as in the author's i9 columns. The Node HTTP path (check-only CAS, `server.cjs`) was NOT re-run, so the author's i9 HTTP root-series (10-15 ms) and mark rows remain AUTHOR-ONLY.
5. Mark: other chats' chunk bodies are 16-byte placeholders as the brief allows (real total about 140 MB not written; effect on list/read cost not measured); parse after the reads of each phase; manifests read in the same mode as shards; mark reads use per-key transactions (`seq`, `par8`) or one transaction (`tx1`), none through localforage; chunking bytes-128KiB primary (the author's mark used count-200, also run).
6. P10 desktop is headed Chrome (both tabs in one window, one hidden); phases 30 s (desktop) and 40 s x 3 rounds (Note 9) rather than "thousands of iterations in one run"; the Note 9 tabs were re-foregrounded in turn before each phase to avoid the hidden-tab callback stall (see P10), so overlap occurred in foreground/background alternation and not with both tabs foregrounded at once (impossible on one phone screen; a split-screen attempt over adb was abandoned: `--activity-launch-adjacent` is unsupported on this Android 10 build).
