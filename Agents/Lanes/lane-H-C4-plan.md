## 2. Re-scope (complexity reduction under MC-091; no product trade-off beyond item 3 below)

The plan's "GC scanners read the stub's `al`" targets paths that cannot run while a stub exists (Q2), and the only store2 keep-set reads the stored index already (Q3). Building a stub-`al` reader for the legacy scanners would add code on unreachable paths, and would need a store2 backend handle the legacy layer does not have. Proposed C4:

1. **Legacy GC defence in depth (tiny).** `buildAssetKeepSet` (`globalApi.svelte.ts`) reports `complete: false` when `db.modules` holds a module stub (that layer can read no stub list). `getUncleanablesSync` tests `isModuleStub` first; for a stub it yields the stub's own `icon` (an index field the stub holds) and reads nothing else, so no missing body key is read through a `$state` proxy and the manual clean-up's live filter (which ignores `complete`) keeps the icon as today. Costs nothing on store2 (never runs there) and keeps the legacy sweeps from deleting a stub's assets should a stub ever reach a legacy page. The other legacy deleters stay behind their page-mode gates, pinned by guard tests that set the real mode with `setPageStorageMode({ kind: 'store2' })` and reset with `resetPageStorageModeForTests`.
2. **Store2 sweep.** No change. Recorded for the future store2 deleter: a stub's assets and inlays are protected by the stored index entry's `al`/`il` (Q3; a carried stub entry keeps its unit live through the commit key's module index, B2's I12 model test); the deleter must keep that, and supply `rederive` or stay incomplete on a stale list (P3).
3. **Integrity scan (`MC-600`).** `collectIntegrityTargets` (`storageMaintenance.ts`) does not load modules. Each module stub contributes only its `icon` (as `getUncleanablesSync` yields it) and its name goes into a new `uncheckedModules` list (a stub with an empty name is listed by its module id; no module counterpart of `coldStorageUnknownCharacterName` exists); the report gains one line from a new `en.ts` key `assetIntegrityReportModulesNotChecked(names)`, shown when the list is non-empty, in both report branches (the `targets.length === 0` branch and the full report). `src/lang/localeParity.test.ts` requires the key in ko, cn, zh-Hant, vi, de and es, so the translator adds the six translations (same arity, `MC-058`) inside this stage, before Gate 2 (F1). No store2 unit or index read (import rule). A follow-up for a copy-only read is recorded, not scheduled.
4. **Lorebook repair at load time.** New leaf `src/ts/process/moduleLorebookRepair.ts` exports `repairModuleLorebook(body): Promise<{ changed: boolean }>`:
   - takes a plain module body, never touches `DBState`, takes no signal;
   - lock-free fast path when `lorebook` is falsy; for an array, `changed` is decided **before** migrating: true iff some entry `v` has `!(v?.bookVersion >= 2)` (missing or below 2). When false, `updateLorebooks` is not called and nothing is assigned. When true, `body.lorebook = updateLorebooks(body.lorebook)` exactly as today (it mutates the entries in place and returns a new array). A non-object entry still throws inside `updateLorebooks` as it does at boot today; at load time that rejects the load (F2);
   - the return value is the only signal: `changed: true` when the lorebook was migrated or reset, `changed: false` otherwise (no lorebook, already migrated, or a corrupted value the user kept);
   - a non-array lorebook runs the existing notice + confirm + diagnostics + confirm sequence, unchanged texts, inside one module-level `Mutex.runExclusive` (FIFO), so the next module's first notice is not posted until this module's last answer resolves.
   `checkNewFormat` calls it for each module in the same sequential loop (a pure move of the loop body; the only behavioural difference is that an unchanged lorebook is not reassigned; contents identical; boot still saves). Replace the stale "single global alert slot" comment with the queued-prompt / unqueued-notice reason.
   **Load-time contract (owner of the call site: lane B, B3):** the loader reads the body, awaits `repairModuleLorebook(body)` **before** installing it, so the slot stays a stub until the body is judged and `acquireModule` resolves only afterwards (no reader, including `acquireModule`'s resident branch, ever sees an unjudged body). C4 edits neither `moduleAcquire.ts` nor any loader and adds no check to `acquireModule`'s resident branch. Lane H re-verifies the call at the rebase onto B3.
   - **What makes the answer stick (F3):** a body for which the function reports `changed: true`, or whose lorebook the user reset, must be saved: B3 must not register it as a clean, already-saved module (its hydrate-as-clean baseline is the stored unit, so the install must mark the module for save). Concurrent loads of the same handle share one load and so one question. These two obligations, with the judge-before-install rule, are a lane B call-site requirement and a **prerequisite of S4d**; lane H records them in its records and in the hand-off to the maintainer for lane B (lane H cannot edit `L3-plan.md` or lane B's records). C4's tests document the contract with a test double only (label D); the proof belongs to B3.
   Residuals, disclosed: a body installed by B3's valve is not judged until the next boot stubs and reloads it; a signal abort during a pending ask cannot cancel the prompt (B3 decides whether a begun ask commits the install); the Mutex orders module repairs only, not other app notices.
