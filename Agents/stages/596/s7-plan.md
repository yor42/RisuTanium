## Requirements and scope

In scope (MC-3734, MC-3735, MC-3796..3799, MC-3950..3957, the orchestrator defaults in `s7-decisions.md`):
1. Per-chat Stop, and the notification Stop (MC-3790/MC-3743), frees a chat whose send or recovered apply waits on a plugin or script hook. That includes hooks reached through the reply path's own requests that carry no signal (memory summaries, imggen, inlay images, emotion and additional-information embeddings) and the plugin MCP tool list and tool calls and the Gemini plugin callbacks (MC-3956). The chat is freed only when the unit's body returns through its own `finally`.
2. After Stop the stopped unit never starts a new hook. It does not speak (preprocessor, provider fetch, postprocessor, playback), auto-continue, resend or run the igp request, and it never writes reply text that an abandoned pass produced. An abandoned script pass calls no further edit handler, and writes nothing through its regex actions (`@@inject`, `@@emo`) or the pass cache (r4).
3. The user sees nothing new (MC-3796). Each abandonment is logged once (`console.warn`). A stopped unit raises no alert (r4: `stableDiff`), and a rejecting MCP tool call, stopped or not, leaves no unhandled rejection for `bootstrap.ts`'s `unhandledrejection` handler to turn into an alert (r5, B19). Exceptions are named in K1: the token-overflow alert an abandoned `hanuraiMemory` can still raise (r5, Gate 1 r4 E4), and whatever a still-running plugin does through its own API. (r6) More generally, nothing stage 7 leaves unawaited, and no callback it registers, can reach the page's `unhandledrejection` or window `error` handler: every such promise and callback goes through the leaf's `detach` (I14), so its failure is one console warning.
4. Stream end (MC-3797, MC-3950): after Stop, the output passes get one 10 s grace that starts at Stop and is shared by every later pass of that unit. A pass still running at the deadline is abandoned. The reply keeps the last raw or processed text already stored, and the chat is freed. A normal Stop with fast scripts keeps today's processed partial.
4b. Non-stream end (MC-3955, r4): under the same deadline, a non-stream reply whose output pass is abandoned is stored raw (unprocessed model text). Nothing paid for is dropped. On Android, a native-owned reply stored this way is consumed only after the save that covers it, as any pushed reply.
5. MC-3951 and MC-3952: a module script run (trigger or Lua) that its unit abandoned can no longer change the chat (chat messages, chat variables in `Chat.scriptstate`, the chat's local lorebook), and it loses its whole access: its access id is removed from every scripting id set, as at a normal finish. This holds whenever the abort lands: while the run waits on the mode mutex (it never runs), while its engine is being created or its module code is loading (it never runs its handler), or during its handler (every later gated call is refused). Plugin listeners, which the app cannot gate, remain a named limitation.
6. C-3 (MC-3798): each `replacerafterRequest` run on a recovered reply gets one bounded wait (60 s). When it expires, the text is stored without that replacer's change.
7. Abandoned hooks keep running (MC-3735). Their own background calls finish and cost tokens. Late writes are limited to the plugin channels named in Risks.
8. (r4) A stopped unit whose body has not returned 20 s after Stop is logged once to the console (watchdog). Nothing is shown to the user.
9. (r5, MC-3957) A composer cancel frees a composer work waiting on the module 'input' trigger or the `editinput` pass: the work resolves `false` at once and appends nothing (D7).

## Approach and stages

### The leaf: `src/ts/process/abortRace.ts` (new, imports nothing from the app)

```ts
export type RaceOutcome<T> = { settled: true, value: T } | { settled: false }
export interface RaceOptions<T> {
    label: string                         // names the hook in the abandonment log
    timeoutMs?: number                    // C-3: abandon after this long whatever the signal does
    onLateValue?: (value: T) => void | PromiseLike<unknown>  // a value the work produces after it was abandoned; a returned promise is handled (r6)
}
/** The work: a function that starts the hook inside it, or (r6) a hook promise that already exists before the race. */
export type RaceWork<T> = ((abandoned: AbortSignal) => T | PromiseLike<T>) | PromiseLike<T>
/** Abandons the work when `signal` aborts. */
export function raceAbort<T>(signal: AbortSignal | null | undefined, work: RaceWork<T>, options: RaceOptions<T>): Promise<RaceOutcome<T>>
/** Abandons the work when `deadline` expires (not at the abort itself). */
export function raceUntil<T>(deadline: StopDeadline, work: RaceWork<T>, options: RaceOptions<T>): Promise<RaceOutcome<T>>
/** (r6) The only way stage-7 code leaves a promise, or a callback's failure, unobserved. Never throws, never rejects. */
export function detach(label: string, task: () => unknown): void
export interface StopDeadline { readonly expired: boolean; dispose(): void }
/** Expires `graceMs` after `signal` aborts, or after creation when it is already aborted. `onExpire` runs once at expiry (r4). */
export function createStopDeadline(signal: AbortSignal, graceMs: number, onExpire?: () => void): StopDeadline
/** A signal that aborts once when any source aborts (or at creation if one already has). */
export function linkedAbort(...sources: (AbortSignal | null | undefined)[]): { signal: AbortSignal, dispose(): void }
export const STOPPED_PASS_GRACE_MS = 10_000   // MC-3950
export const STOPPED_UNIT_WATCHDOG_MS = 20_000 // r4, console only; longer than the grace
```

Rules. Each one is pinned by a test and a mutant, except where a rule names a Gate 2 diff check.
- R-L0 (r6, the S1/N1 class). `detach(label, task)`:
  - calls `task()` synchronously, inside a `try`. A synchronous throw is caught and logged once with `console.warn(label, error)`;
  - if the result is a thenable (its `then` is a function; the check sits inside the same `try`, so a throwing `then` getter is caught too), attaches exactly one terminal rejection handler, `Promise.resolve(result).then(undefined, onFail)`, where `onFail` logs `console.warn(label, error)` once. For a native promise, `Promise.resolve` returns the promise itself, so the handler is attached to it and the engine never reports it. The promise that `.then` returns cannot reject, because `onFail` cannot throw;
  - every log call sits in its own `try` with an empty `catch`, so a throwing `console.warn` (a test spy, a patched console) is swallowed. `detach` never throws and never leaves a rejected promise;
  - returns `void`, so no caller can await it by mistake. A fulfilled result or a plain value is ignored, with no log;
  - logs at most once per call (a synchronous throw and a rejection cannot both happen).
  It is the stage's one primitive for unobserved work. I14 states what must use it, and section "Detach points (r6)" enumerates every use. Pinned by DT-1..DT-3, M85, M86.
- R-L1. If the trigger has already fired (`raceAbort`: the signal is aborted; `raceUntil`: the deadline has expired), `work` is not called and the result is `{settled:false}`. So a stopped unit never starts a new hook.
- R-L1b (r6). When `work` is a promise (a hook started before the race), there is nothing to call or skip. The leaf subscribes to it through `detach` (R-L5) on every path, including the R-L1 short-circuit, so a promise handed to a race is always handled. `abandoned` (R-L8) is aborted as on any abandonment; nothing receives it. Sites pass an existing promise as the promise, never as `() => promise`: wrapped in a function, R-L1 would skip the function and leave the promise with no handler. Only B8 has such a promise (DP-4). Pinned by L-19, S-I2, M87.
- R-L2. `work` is called inside the executor. A synchronous throw becomes a rejection.
- R-L3. If the work settles first, the result is `{settled:true, value}`, or a rejection with the work's own error unchanged. The existing catch paths depend on this.
- R-L4. If the trigger fires first (abort, deadline expiry or `timeoutMs`), the result is `{settled:false}` at once.
- R-L5 (rewritten in r6 on R-L0). The leaf attaches exactly one subscription to the work's promise, and makes it through `detach`: `detach(label, () => promise.then(onValue, onError))`. Before abandonment, `onValue` resolves the race `{settled:true, value}` and `onError` rejects it with the work's error (R-L3); both return nothing and cannot throw. After abandonment, `onValue` returns `options.onLateValue?.(value)` and `onError` rethrows the error. So a late rejection, a synchronous throw of `onLateValue` and a rejection of the promise `onLateValue` returns all reject the subscription's own promise, which `detach` logs once with `console.warn(label, error)`. Nothing else in the leaf attaches a handler to the work's promise, so no handler the leaf creates can leave a rejected promise behind. The abandonment itself is logged once with `console.warn(label)`. There is never an unhandled rejection, and nothing is shown to the user. (r6: the late-rejection log is `console.warn`, where r5 had `console.error`. Both are console only under MC-3796; one channel for every detached failure keeps `detach` the single sink, as the brief directs.)
- R-L6. On every outcome the listeners are removed and the timers cleared. The leaf uses the global `setTimeout`/`clearTimeout`, never `AbortSignal.timeout` or `AbortSignal.any`, so Vitest fake timers drive it and older Android WebViews need nothing new. (r6) Every `setTimeout` callback and every `abort` listener the leaf registers (the race's signal listener and `timeoutMs` timer, the deadline's arming listener and expiry timer, `linkedAbort`'s source listeners) runs its body as `detach(label, body)`, so a throw in it never reaches the window `error` handler, which reports any error with `alertError` (P49). That half is a Gate 2 diff check: those bodies cannot throw without mutating the leaf (DP-5..DP-7, DP-9).
- R-L7. With a `null`/`undefined` signal and no `timeoutMs`, `raceAbort` is a plain await. The many `requestChatData` callers with no signal keep today's behaviour unless a call site below races them.
- R-L8. `abandoned` aborts exactly when the race resolves `{settled:false}`, and never when the work settles first. It is a notice to the work, not a unit identity. It never reaches `abortChat`, the registry or a stop callback, so "mint no other unit controller" (handoff section 3) holds.
- R-L9 (E1). A `StopDeadline` is armed once, at the abort (or at creation if the signal is already aborted), and expires `graceMs` later for every race that shares it. `dispose()` clears its timer and listener.
- R-L10 (S1). `linkedAbort` aborts once when any source aborts. `dispose()` removes its listeners. It never aborts any source.
- R-L11 (r4). `onExpire` runs exactly once, at expiry, and never after `dispose()`. A throw from it is caught and logged. (r6) The leaf calls it as `detach(label, onExpire)`: a throw is logged once with `console.warn`, and a promise it returns is handled too (DP-8; L-18, M86, M88).

Inside a callee that already receives the request's signal (`requestChatData`'s `abortSignal`, `arg.abortSignal` in a provider module, the tool loop's `toolLoop.signal`), race on that signal. Never `callerSignal`, never `arg.signal` in `sendChat`, never a fresh controller.
- On `{settled:false}`, return through the body's normal `return`, so its `finally` runs. Run no later step of the unit.
- (r6) `work` starts its hook inside the function. A hook promise that already exists before the race is passed as the promise itself (R-L1b; only B8). An `onLateValue` returns any promise it starts and never leaves one as a statement (R-L5 handles a returned promise; B13). Nothing else at a site is detached (I14).
- Where the hook is a module script run (a trigger run, a `runLuaEditTrigger` call, or a `processScript`/`processScriptFull` pass), pass the race's `abandoned` signal, or `arg.signal` for `runTrigger` (equivalent there, because trigger races have no grace). That way the run cannot change the chat after it is abandoned (MC-3951).

### Mechanism check after the second rejection (r3, kept)

This is the second consecutive SUBSTANTIVE rejection, so I reconsidered the mechanism before patching. Access-id revocation is still the right one. MC-3952 states the rule as "its id is removed from every scripting id set, as at a normal finish", and every gated binding already refuses an id that is not in the sets (`scriptings.ts:266-279, 356-421, 461-551, 555-1133`), so revocation reuses the existing gate with one removal and no per-binding edit. N1 is not a flaw in revocation. It comes from checking the signal at one point and subscribing at another across the engine setup awaits (`:244`, `:1284`, `:1287`). Of the two alternatives: (1) registering the listener before the id exists still needs a check at the point the id is minted, because the listener has nothing to revoke until then. It adds a mutable "key or nothing yet" closure and closes no extra window. (2) Gating in `runScripted` on the signal itself means storing the signal on the cached engine state and adding a `signal.aborted` test beside each of the 33 id checks in the bindings (Grep of `Scripting(SafeIds|LowLevelIds|EditDisplayIds).has(` in `scriptings.ts`: 33, COMPLETE for the file), beside the id gate. That is a second gate for the same rule, and a missed binding stays open. The simplest form that closes every window is the one Gate 1 r2 sketched (its "Simpler path" says "a local idiom, not a rewrite"): keep the acquisition check, and add one synchronous block at the mint: check `aborted`, return the no-op if set, otherwise mint, register and subscribe, with no `await` anywhere in that block (A2b, A2c). I chose to check just before the mint rather than after it (Gate 1's option (a) moved two statements earlier). An aborted run then never holds a live id even briefly, and the existing `finally` has nothing extra to clean up. Every abort time is covered: before acquisition and while queued (A2a), during engine creation or module load (A2b), during the handler (A2c listener), after the run (the id is already gone). The advisor re-checked this and asked that it not be reopened.

### Mechanism check after the second rejection (r6)

Gate 1 r4 (S1) and r5 (N1) rejected the plan twice in a row for one defect class: a promise or callback the stage leaves unobserved, whose failure reaches `bootstrap.ts`'s handlers and becomes an `alertError` dialog. Gate 1 r5 reconsidered the mechanism and found the class independent of it, since any cancellation scheme must clean up after late values. I agree that the race on the unit's signal stays. Rules:
- The promise `work` returns, the call with `.finally(release)` attached, is the only promise derived from the call, and it is the one raced. The race handles it on every path (R-L3 when it settles first, R-L5 after abandonment), so a rejecting `callTool` never leaves an unhandled rejection, stopped or not. - The count is taken inside `work`. If R-L1 ever skips `work` (the signal already aborted when the race starts), no call starts and no count is taken. - `Promise.resolve().then(...)` turns a synchronous throw of `callTool` into a rejection that still passes through `release`. It starts the call one microtask later than today, which no caller observes. (r6, Gate 1 r5 E2) An equivalent form that keeps today's synchronous start is `(async () => target.callTool(methodName, args, callCtx))().finally(release)`: the `.finally` attaches to the async arrow's own promise, so a synchronous throw of `callTool` still passes through `release`. Attaching `.finally` to the value `target.callTool(...)` returns is not acceptable: a synchronous throw would skip `release` and leak a count. - Racing the whole `sendChatBody`: it would release the unit while the body still writes.

## Invariants and compatibility

- I2. Every race uses the unit's signal, the unit's deadline built from it, or (inside a callee) the request's or tool loop's signal that the unit's signal feeds.
- I3. The app never writes because of an abandoned hook's result. A module script run that was abandoned changes no chat data and holds no live access id after its abort, whenever the abort lands (A2a, A2b, A2c, A5). An abandoned script pass calls no further handler and runs no regex action or cache store (A4 C1/C2). What remains is listed in Risks K1.

- I6. Script capability. An access id still grants nothing outside its own run. The only change is that abandonment ends the grant earlier, or prevents it (A2a, A2b). No id gains a capability. Edit-display ids are untouched in practice (no unit passes a signal to an `editDisplay` run).

- I10 (r4). A non-stream reply after Stop is either stored processed (its passes finished inside the grace) or stored raw (MC-3955); it is never dropped by the output pass. - K1 (changed in r4). What can still write after Stop. The race on chat-writing hooks is accepted (Gate 1 r1 S4). After MC-3951, MC-3952 and A4 the remaining late effects are:
  - plugin listener and plugin API writes (named limitation, MC-3951), including the side effects of a v2 edit handler, a body interceptor, an MCP tool or a `getToolList` that is still running after its abandonment (its return value reaches nothing: the pass returns at C2, the shared interceptor loop returns, `callOnClient` has returned);
  - the trigger tail's `CurrentTriggerIdStore` restore and `ReloadGUIPointer` bump (`triggers.ts:3012-3018`: UI state, no chat data);
  - inlay assets an abandoned image generation writes (K10);
  - calls an abandoned script started before its abort (an LLM request, an image generation) finish and cost tokens (MC-3735), but their result reaches nothing, because the id that would write it is revoked (MC-3952);
  - (r5, Gate 1 r4 E4) the abandoned memory summaries. An abandoned `hypaMemoryV2`/`hypaMemoryV3`/`supaMemory` goes on issuing its remaining signal-less summary requests. Each one runs the before- and after-request replacers, the request trigger, a plugin provider and the body interceptors after Stop, and costs tokens; its result reaches nothing, because the caller's write is cut by the race (B6). An abandoned `hanuraiMemory` can still raise its token-overflow `alertError` (`hanuraiMemory.ts:64-68`, after its awaits at `:41` and `:49`). Both follow from S3 option (a), which Gate 1 r1/r2 accepted, and fall under MC-3735; named in the PR, no mechanism change;
  - the dynamic-asset name cache (`bestMatchCache`) and the pass cache can receive a value from an abandoned pass only after C2, that is from complete Lua and plugin stages, so the value is correct for its key.
- K2. A dropped value: the request path is thrown away (`'Aborted'`); an apply returns `'deferred'`; stream end follows MC-3797/MC-3950; non-stream end follows MC-3955 (stored raw); C-3 follows MC-3798.
- K3. A recovered reply whose hook hangs every time hangs again on every later pass, and each pass needs its own Stop (today's `'deferred'`, now reachable).
- K4 (rewritten in r4, MC-3955). Non-stream after a hung output pass: the raw model text is stored after Stop + grace. For an Android native-owned reply the push runs `noteReplyPushed`, so the key waits for the save and the record is consumed after it (`pageState.ts:203-212, 226-230`); r3's "paid reply lost" and "reconcile reruns the hung pass" outcomes no longer occur. The stored raw text has no output-script processing and no inlay generation; an `<ImgGen=...>` tag stays as text.
- K5. The 10 s deadline keeps the chat busy up to 10 s after Stop, only when a pass hangs. A legitimate pass slower than what remains of the deadline stores raw or older text.
- K6 (wording added in r4). C-1 remains for the holder. A queued waiter no longer runs its script, but it still waits in the FIFO queue. After one abandoned run that never returns, the mode's mutex is held until restart, so later replies in any chat that run Lua in that mode stall until their own Stop. That bounds what "Stop frees the chat" means in the worst case and goes into the PR text in those words (stage 6).
- K7. C-3 60 s: during a replacer hang, the serial pass holds the reload-edge refusals for up to 60 s per replacer.
- K8. Each race adds one abort listener and one internal controller per hook call. The `editprocess` loop adds one per sent message, which is negligible next to the pass.
- K9. Test fragility: fake only `setTimeout`/`clearTimeout`. Real-wasmoon tests must keep the per-file mode names apart (engines are cached per mode, `scriptings.accessIds.test.ts` header), and MS-3..MS-3d need code strings the file has not run before (fixture rule).
- K10 (changed in r4). An abandoned inlay or imggen generation keeps running. It may write an unreferenced inlay asset or set the display image later. That is the app's own write, not chat data. `stableDiff` no longer alerts after Stop (B21). An inlay generation can still start after Stop when the Stop lands during a non-stream pass that finishes inside the grace (`runInlayScreen` runs on the processed text); its placeholder follows MC-3953.
- K11 (E4, plugin-visible). Chat-output listeners are no longer called for a non-stream reply when Stop lands during its output pass or trigger. That matches the stream path (`:3133-3135`). A memory plugin may notice it.
- K12. `setVar` refusal is silent, like the existing refusal for unknown ids. A module that reads back its own variable after a Stop sees the old value. The run is abandoned, so nothing in the app reads its result.
- K13. 7a changes `runTrigger`/`runScripted` for every caller that passes a signal, including the composer 'input' trigger and `/trigger` command lines. The rule is the same for them: after their own abort, a run writes nothing.
- K14 (MC-3954, limitation). A plugin tokenizer (`tokenizerFunc`) that hangs keeps the chat busy after Stop, because `tokenize` takes no signal and is called from many places (`tokenizer.ts:166`). The same holds for `runChroMemorySafely`, which only counts tokens. Named in the PR. The watchdog (E5) logs it on a device.
- K15 (r3). An abort that lands during engine setup leaves the newly built engine cached with its module code loaded (A2b returns after `ScriptingEngineState.code = code`). The next run of that code reuses it, as after any normal setup. The module's top-level code has already run once with no access id, so it could call only the ungated bindings, as it can today at every first load. The Python branch is covered by the same A2b statement, but no test drives Pyodide (no harness); named in the PR.
- K16 (r4; wording r5 per Gate 1 r4 E3). A non-stream reply stopped during its output passes skips `runCurrentChatFunction`, so the stopped unit does not expand its variable CBS. The CBS is deferred, not dropped: the next send expands it at its entry (`runCurrentChatFunction` at `index.svelte.ts:1294`, which runs `expandChatVariables` over every message), as it already does for a reply stored by a stopped stream (`:3133-3135`). This applies also when the passes finish inside the grace.
- K17 (r4). The watchdog is a console line only; it changes no behaviour, and on a device it is visible only through logcat or a remote inspector.
- K18 (r4, plugin-visible). The `callOnClient` race covers every MCP client that runs under a tool loop with a signal (plugin, internal and remote), not only plugin clients: a slow remote tool call is also abandoned at Stop, and the model's tool loop ends as `'stopped'`. The abandoned call keeps running and holds its client's `inFlight` count until it settles (I12).
- K19 (r4). The `'meta_gemini_stream'` race (B17) changes nothing a user sees: the body was already freed at Stop by `readLatest`'s cancel. It lets the Gemini stream close instead of staying open until the callback settles.- K20 (r6). `detach` turns every failure of detached work into one console warning. A programming error inside a detached callback (an `onLateValue`, an `onExpire`, a listener) is therefore not shown to the user, even in a debug build; it is visible only in the console or logcat. That is the intent for work after Stop (MC-3796). Work the unit still awaits is not detached, so its failures keep today's handling (I4).
