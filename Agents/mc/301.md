### MC-4381 — #301 The idle-net verdict after a save is staged too, and the entry's live fields are read before the first yield, 2026-11-27

- Tag: decisions (session, Tier 2, Gate 1 round 1 findings F1 and F2). Date: 2026-11-27. Exact times: UNKNOWN. Sweep ref: none. Related: `#301`, `MC-4380`.

**What was decided.** (1) After a save the shadows reset, so the next idle-net slot re-emits the whole character in one synchronous task of about the same cost as the save pass (0.9 to 1.7 times, measured on the PC). That task is inside the issue's flow within about 32 s of the keystroke, so it is staged in this PR: `saveEncoder.verdictOfYielding` runs the same generator, `netDecision` awaits it under a yield budget that honours `yieldImmediately`, and a belt drops the shadow and answers unknown if the previous encoding moved or a pending commit appeared during the waits. (2) The four live entry reads (`type`, `characters`, tags, creator) are taken in the same synchronous stretch as the plain read, before the first yield, so a live edit during a yield cannot tear the shard entry from its core unit; the verdict does the same.

**Known limitations, named in the PR.** The parked-page judgement (`judgePage`, `slotUnchanged`), `characterBodyMatches` in fast-forward and the residency verdict stay synchronous (outside the issue flow). One very large single chat is still one verdict stage. The idle-net slot does not re-check reply hold or a due pass after its verdict (the outcome window is unchanged, no data is at risk). Two existing yield tests lost per-yield ordering assertions; the snapshot guards edit five entry fields.
