### MC-4360 — #768 The Vertex token mint goes through fetchNative, not globalFetch, 2026-11-27

- Tag: decisions (session, Tier 2 under the ticket's own scope; the brief required the shared transport). Date: 2026-11-27. Exact times: UNKNOWN. Sweep ref: none. Related: `#768`, `MC-4185`, `MC-2965`, `MC-1451`, `MC-3070`.

**What was decided.** The Vertex token service (`src/ts/process/request/vertexToken.ts`) mints through `fetchNative`, the transport the Vertex request itself already uses, so the mint runs `assertNoSecretRef` and the proxy and native routing. `globalFetch` was rejected because every route except the proxy one JSON-stringifies the request body, so a form-encoded token request would go out as a quoted string or `{}`; fixing four shared route functions would widen the change to every `globalFetch` caller and plugin. The mint carries no native-reply ownership and no signal, so it still completes in the page before the request handoff (MC-1451). Persisted fields, the RS256 signer and encryption are unchanged.

**Evidence.** Gate 1 verified the route serialisation in `globalApi.svelte.ts`; Gate 2 round 2 is `[APPROVE]` after one substantive finding was fixed.

### MC-4990 — #768 The minted plain-key Vertex token is memory-only and written empty, 2026-11-28

- Tag: decisions (maintainer, asked by lane A with AskUserQuestion; Tier 2 critical contract). Date: 2026-11-28. Exact times: UNKNOWN. Sweep ref: none. Related: `#768`, `MC-4360`, `MC-3070`, `MC-774`.

**What was decided.** The token minted for a plain service-account key is no longer written to `db.vertexAccessToken` and `db.vertexAccessTokenExpires`. The service keeps one memory token for a plain and a referenced key alike, tagged with the credential (the reference, or a sha-256 digest prefix of the plain key) and the email, so a replaced key never receives the old key's token. The two fields stay in the `Database` type and are always empty and 0, so upstream's `.bin` still reads them (MC-774). A restart mints once on the first Vertex request; that is the accepted cost. A request preview now shows an empty bearer value.

### MC-4991 — #768 A stored Vertex token is never read and is cleared at load, with the boot write marked, 2026-11-28

- Tag: decisions (session, the Gate 1 reject made it concrete). Date: 2026-11-28. Exact times: UNKNOWN. Sweep ref: none. Related: `#768`, `MC-4990`.

**What was decided.** A non-empty `vertexAccessToken` that an older build saved, or an upstream `.bin` carries, is never used: the service does not read the database field. `setDatabase` clears it unconditionally (`legacyVertexToken.ts`), so no later save, export or plugin read carries it. The clear exists only in memory, and the dirty effect's first run marks nothing, so the load records the clear and the boot marks its write (`markBootWrite`, as for minted preset ids and the connections migration). Without the mark the plaintext token stays on disk until an unrelated setting changes (Gate 1 finding 1). Older numbered backups and superseded store2 units keep an expired value until they rotate (a token lives about one hour and is never read). A build never fails on an existing stored token. `invalidateVertexToken` still blanks the two fields, which is harmless and keeps the six UI callers unchanged.

**Evidence.** The boot test T1 fails on the base and passes after; mutants (boot mark dropped, flag not recorded, clear dropped) are all killed in a scratch copy.
