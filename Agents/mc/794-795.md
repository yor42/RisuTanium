### MC-4290 — #729/#730: aliased registry paths share one restore slot, 2026-11-27

- Tag: history-core, critical contract. Date: 2026-11-27. Related: `#729`, `#730`, `MC-350`, `MC-011`.

**Decision.** Paths that share one holder property share ONE restore slot and one working-copy entry. The slot of a path is `restoreSlotOf(path)` in `fieldAccess.ts`: the last registered path with the same (holder, property); a path with no alias and every session-only path is its own slot. It is derived from the registry (`holders` + `property`), not from a list of names. Slot keying is applied in `makeWorking`, `deriveRestoreWrites` (set branch), `noteRestoreWrites`, `revertStepOps` and the `parseRestore` fold. `planRestorePoint`, `listChangedElsewhere` and `RESTORE_PATH_ORDER` are unchanged, because a restore point holds only slot keys.

**Consequence.** On main no two paths share a holder property, so every slot is the identity and no stored record changes. Once an alias row lands, a main-era restore point keyed by the base path folds onto the alias slot on load; when both keys of one group are stored, the slot's entry wins and nothing is refused (MC-011: only unmerged builds can write both). The alias rule is written in the `fieldRegistry.ts` header: an alias has the same `holders` and `value` and accepts every reading of the earlier rows (`keepForeign`, `editWhenAbsent`, same `absent`). Pre-fix-path builds refuse a point or step that names the later alias whole and keep it aside (forward-only, MC-350).
