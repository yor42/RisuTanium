### MC-4330 — #616 Deleting a running reply stops it; a finished reply is discarded with its message, 2026-11-27

- Tag: decisions (maintainer via AskUserQuestion in the #616 session, every answer the recommended option). Date: 2026-11-27. Exact times: UNKNOWN. Sweep ref: none. Related: `#616`, `#514`, `MC-3563`, `MC-4331`.

**What the maintainer chose.**
- Q1: if the reply already finished (record `done`) between the running note showing and the delete, the delete discards the record with the message; the finished reply is not added back.
- Q2: the partial text of a stopped reply is dropped silently, with no "stopped" note and no new `en.ts` key. Consequence: tokens the dropped partial (or the discarded finished reply) used are not settled into the usage meter.
- Q3: only message deletes stop a running reply: a single delete and "this and following". Chat delete and character delete stay as they are, because reconcile already parks or consumes records whose target is gone.
- Q4: no extra confirmation. The existing delete confirmations stand.

### MC-4331 — #616 The native retire after a delete is fire-and-forget; the crash window is a known limitation, 2026-11-27

- Tag: decisions (maintainer via AskUserQuestion in the #616 session, "Accept, note it (Recommended)"). Date: 2026-11-27. Exact times: UNKNOWN. Sweep ref: none. Related: `#616`, `MC-4330`.

**What the maintainer chose.** The delete saves the chat at once and asks the native side to stop and retire the reply without waiting. If the process dies in the milliseconds between the save and the native discard, or the native cancel fails or times out and no later pass in this page discards the record, the next launch re-adds the reply. Not chosen: making delete wait for the native result (async delete API, about 10 call sites, UI wait of up to 2 s).

**Also a known limitation, no decision needed.** Message removals that do not pass through `deleteNow` or `deleteAtSettle` (shift-click remove, `/cut`, `/del`, Lua `removeChat`/`setFullChat`, trigger slices, chat wipe) do not stop a running reply. A request registered but not yet open is not cancelled, which the reload scenario cannot reach.
