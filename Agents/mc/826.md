### MC-4710 — #826 The boot keeps the update-check order; the update flow is not deferred past the first Home frame, 2026-11-28

- Tag: decisions (maintainer ruling asked by the #827/#826 session with AskUserQuestion, recommendation taken). Date: 2026-11-28. Exact times: UNKNOWN. Sweep ref: none. Related: `#826`, `#508`, `#827`.

**What was decided.** Boot keeps waiting for the whole update flow (offer prompt, download, install) before saves run, as `update.ts` documents and `bootstrap.updateOrder.test.ts` pins; the wait on an update day stays bounded by the existing 10 s. The measured cost with no offer pending is about 11 ms on a Note 9 (release build, 1000 synthetic characters, phone offline), too small to justify the risk that a late accepted offer ends the process (`relaunch()` or the system installer) while a save, put-back or streaming reply is active. No deferral, no replacement guarantee, no test rewrite.

**Evidence.** The #826 issue body (measurement and static trace from #508); the maintainer's answer to the question in this session.

### MC-4712 — #827 The boot reads the session's tree bytes and top-level keys once; the Note 9 gain is not measured, 2026-11-28

- Tag: decisions (session, Tier 2 critical contract; PR #881, merged). Date: 2026-11-28. Exact times: UNKNOWN. Sweep ref: none. Related: `#827`, `#826`, `#508`, `MC-350`.

**What was decided.** The session hands the tree bytes its `readTree` judged to the boot's byte read once (row 5, intact tree), and on Tauri classifies the fence and commit key from the re-flush's own read when that key ended `flushed` or `absent` with a bytes token. A `failed` key is read again and is never taken as absent. Every unit is still checked against its Ref and no write or format changes. `previousOfTree` after Home was not done: it changes when an assemble failure shows, which is a product question, and 97 ms is not justified without a measured split between parse and hashing.

**Contract note (Gate 2).** Classification now reads the commit key before the fence, following the re-flush order; before, the fence was read first. No harm was found: on a live Tauri page no other writer exists after the page registers, and in a race with a newer page the commit-then-fence order is the stronger one for the exit protocol, which writes the fence before the marker. The reused read becomes a compare-and-write base, which relies on Tauri and memory tokens comparing bytes, so only a bytes token is reused.

**Known limitations.** The Note 9 gain is not measured; the plan's 75-90 ms of the 517 ms is an estimate. Desktop numbers (i9-13900KF, injected latency 20 ms plus 0.2 ms per key, memory backend) show 3 of 41 backend calls removed and are not device numbers. The boot sweep timing (#796 note 3) is a native call that node cannot time and needs the device.

**Evidence.** Gate 1 round 1 [REJECT] on test text, mechanism accepted; Gate 2 [EDITORIAL] (the order note above, the `reflushKey` comment wording, which PR #881 already carries, and no measured-gain claim).
