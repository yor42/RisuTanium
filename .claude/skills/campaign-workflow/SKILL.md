Carry out the explicit task: $ARGUMENTS
Consult [workflow README](../../../docs/workflow/README.md), [routing](../../../docs/workflow/routing.md) and [gates](../../../docs/workflow/gates.md) as needed. Start with relevant authority/MC entries, then separate discovery, implementation, independent review and arbitration contexts. Use tiny inline lookups and bounded leaf delegation for context-heavy mechanical work. Apply the task's actual authorization; this skill does not authorize unrelated edits, publishing or git commits.
Before substantial Gate 1 work, obtain targeted mechanism/size evidence: trigger, load-bearing source/runtime premise, affected endpoints/subsystems, smallest coherent shared-cause correction and viable stages. Settle decision-critical user-visible skip/repair/refuse/pause choices. Missing product decisions block only the dependent plan/implementation; continue independent work. Preserve the tiny low-risk carve-out rather than inventory speculative rare edges.
Produce the concrete requested result and actual verification evidence. Technical acceptance does not make it COMPLETE: name a record owner and update applicable decisions, gate disposition, authoritative status and current-state/remaining-work records under [records](../../../docs/workflow/records.md). Independently verify changed record claims incrementally; no automatic Gate 2 restart for administrative/editorial closure.
Apply [ownership](../../../docs/workflow/ownership.md): one application-code writer per checkout, including tests; disjoint named documentation writes and read-only helpers may run concurrently. Separate application items require explicit starting revision and integration owner in separately authorized worktrees. Do not create isolation or commit automatically.
