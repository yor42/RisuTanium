# Android system surfaces — spec

Status: **draft for review** (2026-10-25). Task: [tasks/2026-10-25-android-system-surfaces.md](../../tasks/2026-10-25-android-system-surfaces.md). Mockup: [mockup.html](mockup.html). Icons: [icons/](icons/) (generated by [tools/make-icons.mjs](tools/make-icons.mjs)). Platform facts: [research/android-notification-docs.md](../research/android-notification-docs.md).

The family: the generation notification (§1–§6), the launcher icon (§7), the splash screen (§8) and the Back/quit toast (§9). Everything here is a proposal unless it cites a DD entry in [DECISIONS.md](../../DECISIONS.md). Items marked **OPEN** need the maintainer.

What exists today, with sources, is in the task file's "Source facts" table. The short version: one ongoing, silent, low-importance notification whose only content is a title ("Generating a reply…" / "답변 생성 중…" or "Working…" / "작업 중…"), the Material sync glyph as small icon, no accent colour, no body text, no progress, and a Stop action for chat and TTS. **Today it carries no live state (no token count, rate or elapsed time).** It lingers 2 s after the last work ends.

## 0. Device baseline (Tab S9 Ultra, One UI 8.5, today's build) — observed

From [device request 01](../../tasks/2026-10-25-device-request-01-tab-s9-baseline.md), run by lane A on build `c7c6f94d4`:

- **One UI 8.5 draws the app's launcher icon (full-colour squircle) in the notification card, not the small icon.** So on Samsung the small-icon redesign (§2.2) shows only in the status bar (not captured), while the card shows the launcher icon (§7). The adaptive launcher icon therefore matters for the notification too.
- Stop is white text with no accent: One UI 8.5 did not apply any accent to the action (no `setColor` is set today; whether it would honour one is still unverified). The contrast question of §2.3 is moot on this device.
- No status-bar chip or Now Bar, as expected without promotion.
- Linger: gone about 1.5–3 s after a normal finish (no visible flip) and 2.6–3.3 s after Stop (sampled every ~0.7 s).
- The notification can be swiped away during a reply; it does not come back, the reply continues (§5.2 confirmed).
- Back toast: visible about 1–1.4 s, a second Back at 1.36 s quit: confirms the 1 s toast vs 2 s window mismatch (§9).
- Splash: only a flat `#282A36` window was captured, then `#101828` loading; the system splash icon was not seen (frames ~0.45 s apart). Launcher icon not themed.
- Not run: lock-screen variants (no secure lock during the run), status bar right side, themed-icon setting.

## 1. Principles

1. **Standard templates only.** `NotificationCompat.Builder` with the default template, plus `setProgress` and `setUsesChronometer`. No custom `RemoteViews`: Android 12+ decorates and height-limits custom views, and they break on OEM shades (Samsung One UI on the Note 9). The one optional extra is the Android 16 `ProgressStyle` path (§5), still a platform template.
2. **Nothing per token.** The notification changes on a state change, and at most once per second for live numbers, if those are adopted (§3). Elapsed time costs no updates at all: the system draws the chronometer.
3. **Private by default.** Character names, chat names and reply text are personal. The lock screen gets a neutral public version (§4).
4. **One accent.** The notification colour is the brand blue from the token set (§2.3), never the warm "people" colour, which DESIGN_PHILOSOPHY reserves for names and avatars and forbids for status.
5. **Korean first-class.** Every label is a locale key with a Korean string; layouts are checked with the longer Korean text (§10).

### 2.1 Unchanged behaviour

Channel `keepalive` (IMPORTANCE_LOW, silent, no badge), ongoing, `setOnlyAlertOnce`, `FOREGROUND_SERVICE_IMMEDIATE`, CATEGORY_SERVICE, FGS type `dataSync`, the 2 s linger and the once-only permission request all stay. The channel name gains a Korean string: "Background work" / "백그라운드 작업" (new `values-ko/strings.xml`; today it is English-only).

### 2.2 Small icon

[icons/ic_stat_risutanium.xml](icons/ic_stat_risutanium.xml) (vector drawable) and [.svg](icons/ic_stat_risutanium.svg). The status mark's frame (an inverted triangle with a triangular hole) plus its solid centre triangle, white on transparent, alpha only. 24 dp canvas, the frame 20 dp wide and centred by its box; band 2.7 dp, gap 1.9 dp, centre 4.2 dp, so the three parts stay separate at 24 px (mdpi, observed in the review render). At 16 px the centre shrinks to about 1 px and merges, and the icon reads as a hollow inverted triangle, still a recognisable silhouette. Phones draw status-bar icons at their density (the Note 9 is about 4x), so the real raster is far above 16 px; confirm on the Note 9 status bar. The gradient core is merged into the solid centre: a two-tone core cannot survive the system's tinting. It replaces the Material "sync" arrows, which say "syncing", not "your reply".

No per-state small icons: the status bar shows the icon at ~16–24 dp where state glyphs would not read, and changing it per state would add notify traffic for no gain. State lives in the title and text.

### 2.3 Accent colour

`#587BFF`, the `--nexus-core-to` end of the brand core gradient. Reasons:

- `--nexus-accent` `#38D9FF` is built for the dark canvas; on a white shade it is 1.7:1 and would be unreadable as action text or app name on Android 10.
- `#587BFF` is 3.7:1 on white, 4.5:1 on `#1F1F1F` and 3.8:1 on `#2B2B2F`. It passes 3:1 for non-text (the icon, the icon circle) but **fails 4.5:1 for the 14 sp Stop label** on white and on lighter dark cards (14 sp medium is not WCAG large text). No single colour reaches 4.5:1 on both a white and a near-black shade, so the brand colour goes to `setColor` as intent and readable text colour is left to the system.
- Stock Android adjusts the notification colour for text contrast against the shade before tinting action text (framework behaviour, **not verified on One UI**). The mockup's action text, `#4361EE` on light shades (5.0:1 on white) and `#8AA2FF` on dark (5.8:1 on `#2B2B2F`), is the author's **hypothesis** of that adjustment, not a measured system value. If a device shows the raw `#587BFF` on Stop, stop relying on `setColor` for text — device check item.
- It is also the colour the launcher and splash already end on.
- Android 12+ derives the small-icon colour from `setColor`, mainly for foreground-service notifications (research §5); with no colour set it falls back to the system theme colour, which is what users see today.

Contrast numbers are computed sRGB relative-luminance ratios against the stated backgrounds, not measured on a device.

## 3. States

Kinds come from `inFlightKinds()` (`chat`, `tts`, `image`, `request`, `translate`, `embed`, `busy`). When several are in flight the highest row wins: **stopping > chat > tts > image > translate > other**. Failed and Stopped exist only inside the 2 s linger (§3.6). Normal completion has no state of its own: the last title stays for the linger, as today.

| State | When | Title (en / ko) | Text (en / ko) | Chronometer | Progress | Action |
|---|---|---|---|---|---|---|
| Generating | `chat` in flight | Generating a reply… / 답변 생성 중… *(existing keys)* | — | from the chat's start | indeterminate (D-5) | Stop / 중지 |
| Speaking | `tts`, no `chat` | Reading the reply aloud / 답변 읽는 중 | — | from speech start | none | Stop / 중지 |
| Image | `image`, no chat/tts | Generating an image… / 이미지 생성 중… | — | from start | none | none (today's rule) |
| Translating | `translate` | Translating… / 번역 중… | — | from start | none | none |
| Other work | `request`, `embed`, `busy` | Working… / 작업 중… *(existing key)* | — | from start | none | none |
| Stopping | Stop tapped, stoppable work not yet ended | Stopping… / 중지하는 중… | — | hidden (`setUsesChronometer(false)`, `setShowWhen(false)`) | none | none for up to 10 s, then Stop returns (§3.3) |
| Failed (linger) | a `chat` unit ended with an error (reply kinds only) | Reply failed / 답변 생성 실패 | Open the app to see why. / 앱을 열어 확인하세요. | hidden | none | none |
| Stopped (linger) | the work ended after the user's Stop | Stopped / 중지됨 | — | hidden | none | none |

New locale keys (all locales; en and ko given above, others translator-owned): `keepAliveSpeaking`, `keepAliveImage`, `keepAliveTranslating`, `keepAliveStopping`, `keepAliveFailed`, `keepAliveFailedHint`, `keepAliveStopped`. (No "Reply ready" string: that would pre-empt D-8.) Existing: `keepAliveGenerating`, `keepAliveWorking`, `keepAliveStop`.

### 3.1 Generating: progress bar vs elapsed time

Both are shown in the mockup. **Decided (DD-004): elapsed time on, bar off.**

- The chronometer answers the real question ("is it stuck?") with information, and costs zero notify calls: the system redraws it.
- An indeterminate bar adds motion without information, takes a line of height, and on the Note 9's One UI 2 shade it animates for as long as the shade is open. It is cheap for the app (system-drawn) but redundant.
- If chosen, the bar is `setProgress(0, 0, true)`, set once on entering Generating and cleared on leaving it.

### 3.2 Live numbers (token count, tokens/s) — **decided, DD-004**

Text only, in the standard template; icons for these metrics would need a custom `RemoteViews` layout, which is out of scope (DD-028).

Not shown today (the page never sends them). If wanted:

- Content: text line "312 tokens · 24 tok/s" / "312토큰 · 초당 24토큰". Where the provider does not stream usage, the page would have to estimate; then the label must say characters, not tokens ("1,204 characters" / "1,204자"), never an estimated token figure presented as exact.
- Rate: at most one `update` per second, only while the number changed, plus every state change. The page coalesces; the bridge already drops updates when not running. Under Android's update rate limit (research §7) with a wide margin.
- Hidden pages: WebView timers are throttled in the background, so updates may arrive late or stop; the chronometer keeps counting regardless. The design must not depend on the number being current.
- Cost on the floor devices: one bridge call and one notification rebuild per second while generating. Small, but not free on a Note 9; low-power mode (§11) turns live numbers off.
- **Decided (DD-004): on**, with the chronometer, no progress bar. Throttle as above; characters instead of tokens when usage is not streamed; off in low-power mode (§11). Under Android 16 promotion the numbers go in the text line, never the chip.

### 3.3 Stop

- The **native service** switches to Stopping on the tap itself (it rebuilds its own notification before forwarding the stop to the page), so the change does not wait for a WebView round trip and a second tap cannot race. Today the action stays until the work ends.
- Stopping lasts until the stoppable kinds (`chat`, `tts`) are gone. If other work is still running (an image, say), the notification then falls back to that work's state.
- **Timeout:** if the stoppable work has not ended 10 s after the tap (the abort did not take, or the hidden page is throttled), the native side restores the previous state with its Stop action, so the user is never left with a stuck "Stopping…" and no control. Today's no-page case (the service stops itself) is unchanged.
- **Who owns the state while Stopping (re-review N1):** native. Page `update`s that arrive during Stopping may change data (title text, live numbers) but never the state or the actions; native leaves Stopping only when the page reports the stoppable kinds gone (its next notice without `chat`/`tts`, or the stop with outcome) or on the timeout.
- **Races (N2):** a `stop` or the stop-with-outcome cancels the timeout. A Stop restored by the timeout is an ordinary Stop again; a second tap sends a second abort, which must be harmless (`abortChat()`/`stopTTS()` on finished work are no-ops; lane A to confirm).
- Stop on non-stoppable kinds (image, translate, other) stays absent, as today. **OPEN, D-7:** whether image generation should become stoppable is a product/behaviour question outside this surface.

### 3.4 Speaking

TTS after a reply keeps the same notification (the 2 s linger already bridges the gap): the title changes from Generating to Speaking, the chronometer restarts at speech start. If identity is on, the avatar and names stay.

### 3.5 Other work

Image and Translating get their own titles because users start them deliberately and recognise them. `request`, `embed` and `busy` stay "Working…": their meanings are internal and a precise label would be a claim the page cannot always back.

### 3.6 Failed and Stopped inside the linger

Today the 2 s linger keeps the last title, so a failed or stopped reply still reads "Generating a reply…" for 2 s.

- **Normal completion: no change.** The last title stays for the linger. A "done" state here would flip the notification between a reply and its speech (Generating → done → Speaking within 2 s), which is the flapping the linger exists to prevent, and a "Reply ready" string would pre-empt D-8.
- **No action during the linger:** whatever the title, the linger card carries no Stop (the work has ended).
- **After the user's Stop:** Stopped / 중지됨 for the linger.
- **After a failed reply:** Failed for the linger, only for `chat` units and only once the page can tell a failure from an abort (it cannot today: `inFlightWork.ts` records no outcome; this is new page work).
- **Transport (review F2, N3):** the outcome travels **inside** the delayed stop, through a new bridge method `stopAfterWithOutcome(ms, outcome)` (not an overload of `stopAfter` on the JavascriptInterface; `stopAfter(ms)` stays for old pages). The page owns the outcome; native only displays it. `KeepAliveBridge.update` cancels a pending delayed stop (`KeepAliveBridge.kt:55-58`), so an `update` sent after `stopAfter` would leave the service running. Native test: `stopAfter` with an outcome rebuilds once and keeps the delayed stop.

This is **not** a reply-ready notification: it disappears with the service after 2 s. A persistent one is D-8 (§12).

## 4. Lock screen and privacy

- Main notification: `VISIBILITY_PRIVATE`, with `setPublicVersion(public)`.
- Public version: small icon, accent, title = the state title (never the character or chat name), no text, no large icon, no preview, chronometer kept. Stop: per D-13, **decided DD-005** (below). Live numbers are not in the public version.
- The public version is used only when the device has a secure lock screen and the user chose to hide sensitive content; with "show all content" the full notification shows on the lock screen. Bridged wearables and notification mirroring may show the full version regardless. On Android 10 the same API applies.
- **D-13, Stop on the lock screen.** Anyone holding the locked phone could abort a reply or speech; the stop intent carries no authentication (`KeepAliveService.kt:112-116`). Options: (a) keep Stop on the lock screen (low harm: a stopped reply can be regenerated, and Stop is the main reason to see the notification there); (b) require unlock with `setAuthenticationRequired(true)` on the action, Android 12+ only, so the Note 9 keeps (a) or (c); (c) remove Stop from the public version. **Decided (DD-005): (b) on Android 12+, (a) on Android 10.** QA note: Note 9 checks never exercise the authenticated path; it needs an Android 12+ device (the Tab S9 Ultra).
- A reply preview (D-3) never appears in the public version.

## 5. Platform variants

### 5.1 Android 10 (Note 9, One UI 2) and Android 12+

See the mockup's side-by-side. Platform rules (header layout, accent tinting, large-icon placement, action icons) are taken from the research file and are approximations of the stock and One UI shades; the mockup is **Android-like, not pixel-exact**.

### 5.2 Android 13+ notification permission

- Unchanged: asked once, on the first work, while the app is in front. A denial hides the notification; the service still runs (MainActivity comment; platform rule in research §3).
- Consequence: no Stop in the shade. While the app is in the background the only system control is the Task Manager (Android 13+), and its action stops the whole app, not the reply. Stopping just the reply needs the app opened.
- Also on Android 13+, users can swipe an ongoing FGS notification away (research §3). The work continues, without a notification. The design does not repost it (the spec relies on Stop being optional, not on the notification staying).
- Proposal: a one-time inline notice in the chat the first time work starts after a denial (the page learns the result through a new `onRequestPermissionsResult` forward), plus the same line kept in Settings › Android, which reads the live state (`areNotificationsEnabled`, a new bridge query, checked on each resume) so a later denial in system settings is also covered; never a dialog, never repeated: "Notifications are off, so background replies have no Stop button in the notification shade. [Open settings]" / "알림이 꺼져 있어 백그라운드 답변을 알림창에서 중지할 수 없습니다. [설정 열기]". **Decided (DD-009).**

### 5.3 Android 16 Live Updates and Samsung Now Bar — optional enhancement (**deferred, DD-010**)

Verified against [the Live Updates page](https://developer.android.com/develop/ui/views/notifications/live-update); details and confidence in research §1–§2.

**What it requires:** `setOngoing(true)`, a content title, `setRequestPromotedOngoing(true)` (androidx.core 1.17+), and the non-runtime manifest permission `POST_PROMOTED_NOTIFICATIONS`. The standard template qualifies; `ProgressStyle` is not required.

**What it forbids:** custom content views, `setColorized(true)`, group summaries, an IMPORTANCE_MIN channel. Google's allowed uses are ongoing, user-initiated, time-sensitive activities with a clear start and end (navigation, calls, rideshare, delivery); forbidden are ads, chat messages, alerts and "quick access to app features". **AI reply generation is in neither list**, so eligibility is a judgment call; users can demote it or switch Live Updates off per app, and Google warns that unwanted ones may cost the app its notification permission.

**Design if adopted:**

- Request promotion only for **Generating** and **Speaking**, the two user-initiated states with a clear end. Never for other work, Stopping, Stopped or Failed (drop the request on those updates).
- The status-bar chip (≤ 96 dp) shows the small icon plus the chronometer (`setUsesChronometer`), which is exactly the elapsed counter of §3.1, so no extra text is needed. No `setShortCriticalText`: an elapsed time says more than a 6-character word, and Korean words do not fit reliably.
- Expanded is the default and cannot be collapsed: the large layout must read well with identity off (title + Stop).
- Everything else in §2–§4 is unchanged; nothing in this spec uses a custom view or colourisation, so promotion costs no redesign.
- Check `canPostPromotedNotifications()`; if the user turned promotion off, post the ordinary notification silently. Do not nag; never repost a dismissed one.
- **Unverified, test on the Tab S9 Ultra:** whether a promoted notification on the lock screen, in the status-bar chip and in the Now Bar honours the public version (§4). Until shown otherwise, keep the title identity-free when promoted (the character name goes to the text line).

**Samsung Now Bar:** Samsung's support page documents the Now Bar (One UI 7+, screen lock required) but names no third-party API or allowlist. Press reports say One UI 8 takes Android 16 Live Updates from any app. Unverified; treat Now Bar as "may appear if promoted" and confirm on a device. Test devices: the Galaxy Tab S9 Ultra (One UI 8.5) as the sandbox for a test build, and the maintainer's Galaxy Z Fold 7 (One UI 8+) for observation only with the installed app, covering the cover and inner screens; the two Note 9s stay reserved for lane A's development baseline (Android 10 checks only, scheduled through lane A). Personal-device checks follow [DEVICE_TEST_RULES.md](../../DEVICE_TEST_RULES.md).

**Recommendation:** optional and **off until** a policy decision (eligibility is a judgment call; misuse can cost the notification permission) and a device check. If adopted, behind the Android 16 check, Generating/Speaking only, after one device check: a test build on the Tab S9 Ultra (Live Update shade, status-bar chip, Now Bar, lock screen), and the maintainer's observation on the Z Fold 7 of how One UI 8 treats the notification on the cover and inner screens. A stock Android 16 device is not available; note that as unverified.

### 5.4 Light and dark

The system draws the shade; the app supplies only the accent and icons. The mockup shows both. `#587BFF` passes in both (§2.3).

## 8. Splash screen

Today: light `#3B82F6` (generic Tailwind blue) / night `#282A36`, the white mark, then `#101828` until the page paints, then the app. Three different colours in the first second.

Proposal: one dark canvas from launch to first paint.

- `splash_background` = `#00011C` (`--nexus-canvas`) in both day and night; `splash_light_bars` = false in both.
- `loading_background` = `#00011C` too, so splash → WebView → boot screen ([mockups/startup.html](../../mockups/startup.html)) is one continuous colour.
- Icon unchanged (`splash_logo`, static). No animated icon: on Android 10 the compat library shows a static icon anyway, and a looping AVD adds start-up work on the slowest devices for no information.
- **Decided (DD-006):** dark for all schemes.

## 9. Back / quit toast

Today: the in-WebView toast, bottom-right, fades in and out over 1 s, while the second press counts for 2 s; no live region; Korean copy "'뒤로' 버튼을 한 번 더 누르면 종료됩니다." (long, wraps on narrow phones).

Proposal (in-app, not a native Toast):

- A pill centred above the bottom inset (16 dp from the bottom of the page, max width `min(90vw, 360px)`), `--nexus-surface-flat` background, `--nexus-text`, a `log-out` Lucide icon at 18 px before the text.
- **Visible for exactly the quit window:** 150 ms fade/rise in, hold, 200 ms fade out ending at 2000 ms (`QUIT_WINDOW_MS`). The timing reads from the same constant.
- `role="status"` with `aria-live="polite"`, so TalkBack reads it once.
- Reduced motion: opacity only, no rise.
- Copy (locale change, **decided DD-008**): en "Press Back again to quit" (unchanged); ko "종료하려면 뒤로 가기를 한번 더 누르세요" (maintainer's wording; drops "버튼", so it fits gesture navigation and the Note 9's button alike). Spacing note for the translator: standard spelling counts the press as "한 번"; the maintainer wrote "한번" — keep as written unless the maintainer changes it.
- Accepted limit, stated for the record: the 2 s window is short for TalkBack users (WCAG 2.2.1); it is today's behaviour and not changed here.
- Alternative considered: native `Toast` via the bridge. It matches `LENGTH_SHORT` (2 s) for free and shows the app icon on Android 12+, but it is styled by the system, cannot carry the in-app icon, and adds a bridge method. Not recommended.

## 10. Korean and long text

- Titles are single-line in the collapsed template and ellipsize; the longest proposed Korean title is "답변 생성 실패" / "이미지 생성 중…" (short). With identity on, the title is the character name; long names ellipsize, the state stays readable in the text line.
- Action labels are one word in both languages ("중지").
- The mockup renders every state in both languages at 360 and 412 px widths.

## 11. Low-power mode

The notification is system-drawn, so low power changes only what the app asks for. The page decides from its own low-power switch (DESIGN_PHILOSOPHY §8), not a new native call; Android's battery saver is not consulted. The Raspberry Pi 3 floor does not apply to these Android surfaces. With low power on: no live numbers (§3.2), no reply preview (D-3), no progress bar (D-5). Chronometer, title, avatar (decoded once) stay.

## 12. Reply-ready notification after completion — **deferred, DD-010**

Not current behaviour: the service stops when work ends and nothing remains. If wanted:

- A **separate**, non-ongoing notification on a new channel ("Replies" / "답변", IMPORTANCE_DEFAULT so it can alert, user-controllable), posted only when the app is in the background at completion, auto-cancelled when the app opens that chat.
- Content: "{Character} replied" / "{캐릭터}의 답변이 도착했습니다", optional preview under the same privacy rules (§4).
- Cost: a new channel and a new non-FGS notification path in native code; the page must report completion while hidden (throttled timers make this late but not lost); on Android 13+ it depends on the same notification permission, so users who denied it get nothing.
- Related existing path: with the `notification` setting on, the page already calls the web `new Notification('Risuai', { body: result })` after a reply finishes, carrying the full reply text (`src/ts/process/index.svelte.ts:2577-2590`). Whether the Android WebView shows it was not checked; a native reply-ready notification would have to replace, not duplicate, it, and its full-text body breaks the privacy rule of §4.
- Recommendation: decide after the base notification ships.
